# 계획: 컷인 확장 — 큰 도트를 볼 기회를 늘린다 (상주하지 않고)

작성 2026-08-28. 발단은 한 줄짜리 불만이다 — **"메뉴바에서만 보니까 작아서 아쉽다."**

이 문서는 그 불만을 "펫 창을 띄우자"로 번역하지 않는다. 번역하면 화면 점유라는 새 비용이
생기고, 그 비용이 정당한지는 따로 증명해야 하기 때문이다. 아래 §1에서 그 증명이 실패한다.

## 0. 목표

**208px 도트를 볼 기회를 늘리되, 평소 화면 점유는 0으로 유지한다.**

```
지금:  진화 순간 ─────────────────────────────────→ 208px 컷인 (1회)
       그 외 전부 ─────────────────────────────────→ 16px 메뉴바

이후:  진화 / 리미트 진입 / 케어미스 / 첫 인사 ──→ 208px 컷인
       그 외 전부 ─────────────────────────────────→ 16px 메뉴바 (변경 없음)
```

새 창도, 새 상주 프로세스도, 새 알림 채널도 만들지 않는다. **이미 있는 컷인 창의 트리거를
1개에서 4개로 늘리는 것**이 이 계획의 전부다.

## 1. 왜 상주 펫이 아닌가

### 1-1. 이 장르는 이미 성숙했고, claudemon은 그 장르가 아니다

2026년 기준으로 "AI 코딩 에이전트에 붙는 데스크톱 펫"은 하나의 장르다.

| 프로젝트 | 규모 | 성격 |
|---|---|---|
| [clawd-on-desk](https://github.com/rullerzhou-afk/clawd-on-desk) | ⭐6.1k | 픽셀 게, 20+ 에이전트 훅 연동. 이 장르의 정본 |
| [codex-pets](https://github.com/codex-pets/codex-pets) / [petdex](https://petdex.dev/) / [agentpets](https://agentpets.dev/) | — | 스프라이트 갤러리 생태계, 200+ 펫 |
| [openpets](https://github.com/alterhq/openpets) | ⭐91 | macOS 전용, MCP/CLI로 펫 제어 |

이들의 공통점은 **상태 표시기**라는 것이다 — thinking / typing / 서브에이전트 2개 / 완료.
초 단위로 변하고, 그래서 상주가 정당하다. 자리를 비웠다 돌아와서 "끝났나?"를 보는 것이
존재 이유다.

**claudemon은 누적 성장 기록이다.** stage는 하루 단위로, 계보는 몇 주 단위로 움직인다.
초 단위로 볼 것이 없는데 초 단위로 화면을 점유하는 것은 비용만 내는 일이다.

정보의 시간 스케일이 다르면 표시 방식도 달라야 한다:

```
변화 주기          적합한 표시
─────────────────────────────────────────
초 단위     →     상주 (계속 봐야 하므로)
시간~일 단위 →     사건 통보 (변할 때만 보면 되므로)   ← claudemon
```

### 1-2. 몰입을 깨는 것은 크기가 아니라 움직임이다

주변시야는 형태보다 모션에 반응한다. 정지한 208px보다 계속 흔들리는 16px이 더 성가시다.
지금 메뉴바 스프라이트는 0.8초마다 프레임을 돌린다 (`menubar/claudemon-menubar.swift:994`).

이 사실은 "크게 하면 방해된다"는 직관을 뒤집는다. 문제는 크기가 아니라 **평소에 얼마나
물러나 있는가**다. 컷인은 평소 물러남이 100%이므로 크기를 마음껏 키워도 된다.

### 1-3. 코드가 이미 이 원칙을 명문화하고 있다

`lib/notify.js:5-10`:

> This is deliberately the ONLY place claudemon touches an OS notification channel.
> The mascot's own state stays on the menu bar icon and the evolution cut-in overlay;
> banners exist purely to say "your turn" when the terminal isn't in front of you.

**마스코트 상태는 메뉴바 아이콘과 컷인 오버레이에만 산다**는 계약이 이미 있다. 컷인 확장은
이 계약 안에 있고, 상주 펫은 계약을 새로 써야 한다. 계약을 고칠 만한 근거가 §1-1에서
나오지 않았으므로 고치지 않는다.

### 1-4. 반면교사

- **Clippy** — 망한 이유는 크기가 아니라 **사용자의 스케줄이 아닌 자기 스케줄로 주의를
  요구했다**는 것. 트리거를 고를 때 이 기준을 쓴다 (§3-1).
- **Johnny Castaway** (1992) — 이어지는 이야기를 **흘끗 볼 때만** 목격하게 하는 구조.
  "점유하지 말고 눈길을 보상하라"의 교과서.
- **Shimeji** (2009) — 실제 창의 가장자리에 매달린다. 화면의 죽은 공간에 산다.

이론적 배경은 Calm Technology (Weiser & Brown 1996, Amber Case 2015):
*"기술은 가능한 한 가장 적은 양의 주의를 요구해야 한다."*

## 2. 지금 무엇이 있나 — 실측

컷인 기계는 **이미 완성돼 있다**. 부족한 것은 트리거뿐이다.

| 자산 | 위치 | 상태 |
|---|---|---|
| 208px 컷인 창 | `makeCutInWindow():1450` | borderless · 투명 · floating · `ignoresMouseEvents` · 전 스페이스 |
| 컷인 재생 로직 | `startEvolutionCutIn():1523` | 실루엣 → 모프 → 홀드 1.2s → 페이드아웃 |
| 재진입 가드 | `cutInGeneration:1449` | 재트리거 시 stale 타이머가 새 실행을 밟지 못하게 함 |
| 208px 초상 | `portraitImage(forStage:):1144` | 전용 초상 없으면 스테이지 도트를 정수배 업스케일 |
| 백드롭 패널 | `makeCutInWindow()` 내부 | 흰 실루엣/어두운 도트가 배경에 묻히는 문제 해결 완료 |

**트리거는 하나뿐이다** — `refreshState():1324-1331`, 같은 몬이 스테이지를 올라갔을 때.

```swift
if currentMon == previousMon,
   let oldIdx = stageIds.firstIndex(of: previousStageId),
   let newIdx = stageIds.firstIndex(of: daily.stageId),
   newIdx > oldIdx, ... {
    startEvolutionBurst(from: oldFrames, to: newFrames)
    startEvolutionCutIn(fromStage: previousStageId, toStage: daily.stageId, name: ...)
}
```

즉 **하루에 많아야 몇 번, 대개 0~2회**다. 208px 도트를 볼 기회가 그만큼 드물다는 것이
애초의 불만이었다.

## 3. 무엇을 추가하나

### 3-1. 트리거 선정 기준

Clippy의 실패(§1-4)를 피하려면 기준이 필요하다. 아래 셋을 **모두** 만족해야 컷인을 준다.

1. **사용자의 스케줄에서 발생한다** — 내가 한 일의 결과지, 타이머가 정한 순간이 아니다
2. **드물다** — 하루 한 자릿수. 잦으면 그 자체로 배경이 되어 의미를 잃는다
3. **놓치면 손해다** — 지나가면 알 수 없거나, 알았으면 다르게 행동했을 정보

### 3-2. 채택된 트리거 4종

| # | 트리거 | 기준 충족 | 예상 빈도 |
|---|---|---|---|
| T1 | 진화 (기존) | 내 토큰 사용의 결과 · 드묾 · 놓치면 모름 | 0~2회/일 |
| T2 | **리미트 진입** (limit80 / limit95) | 내 사용의 결과 · 드묾 · **알았으면 페이스를 바꿨을 정보** | 0~2회/일 |
| T3 | **케어미스 분기** (T1의 변종) | 내 방치의 결과 · 드묾 · 계보에 영구 영향 | 드묾 |
| T4 | **오늘의 첫 인사** | 첫 세션 시작 시 1회 · 하루 1회 · 오늘 뭐가 됐는지 알려줌 | 1회/일 |

**T2가 이 계획에서 가장 값이 크다.** 지금은 리미트 80%를 넘어도 메뉴바 프레임만 조용히
바뀌어서 놓치기 쉽다. 알았으면 fan-out을 줄였을 정보를 놓치는 것은 실제 손해다.

### 3-2-1. T3는 퇴화가 아니다 — 독립 리뷰에서 정정된 항목

이 계획서의 초안은 T3를 "케어미스 **또는 퇴화**"로 썼다. **둘 다 틀렸다.** 실측으로 정정한다.

**① daily 스테이지는 퇴화하지 않는다.**

```
applyRegression (lib/evolve.js:120)
  └─ 호출처: hook.js:78, statusline.js:72
  └─ 대상:   lib/state.js 의 state.json / sessions/*.json   ← 세션 상태
                                                                (STATE_FILE:6)

메뉴바 refreshState()
  └─ readDailyState() → daily.json                          ← 일일 상태
                                                                (menubar:105)
  └─ lib/daily.js:5 는 applyRegression 을 import 하지 않는다
```

두 상태는 별개다. 세션 상태는 방치 시간으로 퇴화하지만 **메뉴바가 보는 일일 스테이지에는
퇴화 경로가 없다.** `daily.json`의 stageId가 내려가는 경우는 둘뿐이고 둘 다 T3가 아니다:
종점 클램프(`lib/daily.js:1199`)와 일일 롤오버(몬 교체 → 알로 복귀, 이미 §2의 조건문이 제외).

> 독립 리뷰는 이 지점을 "감지는 원리상 가능하나 설계가 빠졌다"로 판정했으나, 그 근거였던
> "`applyRegression`이 `daily.json`의 stageId를 낮춘다"는 사실과 다르다. 위 호출처 대조로
> 기각한다. 결론(T3에 설계가 빠졌다)은 유효하고, 실제 상황은 리뷰 판정보다 더 나쁘다 —
> 설계가 빠진 것이 아니라 **전제가 존재하지 않았다.**

**② 케어미스는 아래가 아니라 옆이다.**

케어미스는 스테이지 하락이 아니라 **경로 선택 게이트**다 (`docs/global-graph-plan.md` §B-7).
축은 `outputPerTurn ≥ 15000` — 프롬프트 몇 개로 10만 토큰을 뽑은 날, 즉 무인 주행 날이다.
참이면 in-edge가 전량 게이팅된 노드(레어몬·누메몬·스카몬 등 쓰레기 계열)로 **진화가 유도된다.**

```
평소:      성숙기 ──(추첨)──→ 가루몬        ← T1 컷인이 이미 뜬다
케어미스:  성숙기 ──(게이트)─→ 레어몬        ← T1 컷인이 똑같이 뜬다
```

즉 **컷인은 이미 뜨고 있다.** 빠진 것은 트리거가 아니라 **"이건 네가 방치해서 나온 형태다"라는
라벨**이다. 따라서 T3는 독립 트리거가 아니라 **T1의 변종 라벨**로 재정의한다.

**③ 그런데 그 라벨을 붙일 데이터가 없다.**

`lib/daily.js:530`의 route 엔트리는 `{ id, name, sprite }`뿐이다. 어떤 엣지를 어떤 조건으로
탔는지가 기록되지 않으므로, Swift 쪽은 오늘의 진화가 케어미스 분기였는지 **알 방법이 없다.**

T3를 하려면 route 엔트리에 게이트 플래그를 추가해야 한다:

```js
route[stage] = { id, name, sprite, careMiss: true }   // lib/daily.js:519,530,537,546,557,562
```

이것은 §7의 "JS 쪽 변경 없음"과 정면으로 충돌한다. 초안의 내부 모순이었다. §7에서 정정한다.

**그리고 이것은 "필드 하나 추가"보다 크다.** 정방향 순회가 후보를 뽑는 경로에서 **엣지 조건이
반환 경계에서 소실된다**:

```js
function candidatesFor(node, ctx, childrenOf) {      // lib/daily.js:433
  const met  = links.filter((e) => conditionMet(e.when, ctx));
  const pool = met.length > 0 ? met : links;
  const tied = pool.filter((e) => JSON.stringify(e.when) === winner);
  return tied.map(e => e.node);                      // :441 — e.when 이 여기서 버려진다
}
```

호출자(`:554`)는 노드만 받으므로 **어떤 조건으로 골랐는지 알 수 없다.** 따라서 T3는
`candidatesFor`의 **반환 계약 변경**(`{node, when}`)과 두 콜사이트(`:536` 종점 판정, `:554`
후보 추첨) 수정을 동반한다. 역방향(prefix) 순회는 `p.when`을 이미 들고 있어(`:505-517`) 더 싸다.

추가로 **의미 결합 문제**가 남는다. `when`을 실어 보내도 소비자가 "이 조건이 케어미스 게이트인가"를
알아야 한다. 케어미스 축은 `outputPerTurn ≥ 15000`(§B-7)이므로, 조건 타입을 하드코딩하거나
그래프 데이터에 명시 플래그를 넣어야 한다. 어느 쪽도 자명하지 않다.

**골든 테스트는 영향받지 않는다** — `test/fixtures/route-golden.json`의 `compare` 필드가
"스테이지별 노드 id 만 비교한다"고 못박고 있어(`test/daily.test.js:1879`) 엔트리에 필드를
추가해도 깨지지 않는다. 이건 T3에 유리한 실측이다.

## 4. 구현

### 4-1. `startEvolutionCutIn`을 종류 있는 컷인으로 일반화

현재 시그니처는 진화 전용이다.

```swift
// as-is
func startEvolutionCutIn(fromStage: String, toStage: String, name: String)

// to-be
enum CutInKind {
    case evolution(from: String, to: String, name: String, careMiss: Bool)  // T1 (+T3)
    case limit(level: String)                                              // T2
    case greeting(stage: String, name: String)                             // T4
}
func startCutIn(_ kind: CutInKind)
```

**T3는 케이스가 아니라 `.evolution`의 `careMiss` 플래그다** (§3-2-1). 연출은 T1과 동일하고
라벨 문구만 갈린다 — "○○로 진화!" vs "○○로 진화… (방치)".

모프 연출(실루엣 → 전환)은 `.evolution`에만 쓴다. `.limit`과 `.greeting`은 단일 이미지 +
라벨이면 충분하다 — 없던 연출을 새로 만들지 않는다.

### 4-2. 엣지 트리거 — 상태가 아니라 전이를 본다

이것이 이 구현의 **유일한 진짜 위험**이다.

`refreshState()`는 **2초마다** 돈다 (`:1004`). 그리고 `updateRateLimits():1607-1619`는
매 틱 `currentLimitLevel`을 nil로 지우고 다시 계산한다 — 이전 값을 기억하지 않는다.

따라서 순진하게 `if currentLimitLevel == "limit80" { 컷인 }` 이라고 쓰면 **2초마다 컷인이
뜬다.** 반드시 이전 값을 들고 있다가 전이할 때만 발화해야 한다.

```swift
// updateRateLimits() 끝에서
let previous = currentLimitLevel
currentLimitLevel = limitLevel(rateLimits: rateLimits, now: now)
if currentLimitLevel != previous, let level = currentLimitLevel,
   level == "limit80" || level == "limit95" {
    startCutIn(.limit(level: level))
}
```

**추가로 경계 진동(flapping)을 막아야 한다.** 사용률이 임계 근처에 있으면 79.6% ↔ 80.1%를
오가며 `nil → limit80 → nil → limit80`을 반복할 수 있다. 게이트 둘을 건다:

1. **레벨별 1일 1회** — `(레벨, 날짜)` 쌍을 기억하고 이미 본 조합이면 발화하지 않는다.
   리미트 진입은 하루에 한 번 알면 충분한 정보다.
2. **하강 전이는 무시** — `nil → limit80`과 `limit80 → limit95`만 발화. 반대 방향은 침묵.

같은 규칙을 T3와 T4에도 적용한다. T4는 날짜만 기억하면 된다.

### 4-2-1. stale 캐시로 발화하면 안 된다 — 독립 리뷰 지적

`mostRecentHudCache():732-747`은 등록된 세션들의 `.omc/state/hud-stdin-cache.json` 중
**mtime이 가장 최신인 것**을 고르고 `(json, stale)`을 돌려준다. 그런데 `updateRateLimits()`는
`stale`을 **메뉴 라벨에만** 쓰고(`rateLimitLine(key:bucket:stale:)`) `currentLimitLevel` 계산에는
게이트를 걸지 않는다.

결과: 며칠 전 세션의 80% 캐시가 "가장 최신"으로 뽑히면 **오늘 일도 안 했는데 리미트 컷인이
뜬다.** 메뉴 라벨은 "(오래됨)"이라 적혀 있지만 컷인은 그 사실을 모른다.

지금까지 문제가 되지 않은 이유는 `currentLimitLevel`이 **프레임 선택에만** 쓰였기 때문이다 —
틀린 프레임은 조용하고, 다음 틱에 고쳐진다. 컷인은 조용하지 않고 되돌릴 수도 없다. **표시를
사건으로 승격시키는 순간 stale 허용치가 달라진다.**

따라서 T2는 stale이 아닌 캐시에서만 발화한다:

```swift
if !stale, currentLimitLevel != previous, ... { startCutIn(.limit(level: level)) }
```

프레임 선택 동작은 건드리지 않는다 — 지금 동작이 옳고, 바꾸면 별개의 회귀 위험이 생긴다.

### 4-3. 상태 지속 — 앱 재시작을 견뎌야 한다

"1일 1회" 게이트가 메모리에만 있으면 앱을 재시작할 때마다 초기화되어 컷인이 다시 뜬다.
개발 중에는 앱을 자주 재시작하므로 이건 실제로 발생한다.

`~/.claude/claudemon/cutin-seen.json` 같은 작은 파일에 기록한다:

```json
{ "date": "2026-08-28", "seen": ["limit80", "greeting"] }
```

날짜가 바뀌면 통째로 리셋한다. 기존 상태 파일 규약(`lib/state.js`)을 따르되, 이 파일은
Swift 쪽만 읽고 쓰므로 JS 계약에 넣지 않는다.

### 4-4. 큐잉 — 동시 발화 처리

두 컷인이 겹칠 수 있다 (예: 진화 직후 리미트 진입). `cutInGeneration:1449`은 나중 것이
앞 것을 **덮어쓰도록** 되어 있다. 진화 도중에 리미트 컷인이 끼어들면 진화 연출이 잘린다.

가장 값싼 해결은 **우선순위 드롭**이다. 큐를 만들지 않는다:

```
진화 > 리미트 > 인사
```

컷인이 재생 중일 때 더 낮은 우선순위가 오면 **버린다**(1일 1회 플래그는 세워둔다).
같거나 높은 우선순위면 기존 동작대로 덮어쓴다.

큐를 만들지 않는 이유: 컷인 하나가 ~3초인데 줄을 세우면 사용자가 3초 뒤에 "왜 지금 이게
뜨지"를 겪는다. 사건 통보는 사건 시점에 뜨지 않으면 의미가 없다.

## 5. 검증

Swift 쪽은 지금 테스트 하네스가 없다. 순수 함수로 분리해 검증 가능한 표면을 만든다.

| **stale 캐시는 침묵** (§4-2-1) | 위 함수에 `stale: true`를 주입 |
| 1일 1회 게이트 · 날짜 롤오버 | 위 함수에 날짜를 주입해 테스트 |
| 우선순위 드롭 | 순수 함수 `resolveCutIn(active:incoming:)` |
| 연출 자체 | 수동 — 기존 `demoCutIn:988` 훅을 종류별로 확장해 눈으로 확인 |
| **케어미스 플래그 전파** (T3 착수 시) | `lib/daily.js` route 엔트리에 `careMiss`가 실리는지 `node --test`로 검증 |

## 5-2. 범위 판결 — 변호인 토론 (2026-08-28)

"1차에 어디까지 배선하는가"를 옵션 3개로 세우고, 각 옵션의 변호인(병렬)과 판정관을 따로 두었다.

| 옵션 | 내용 | 판정 |
|---|---|---|
| **A** | T2만 | **채택** |
| B | T2 + T4 (Swift 단독 전량) | 기각 |
| C | T2 + T3 + T4 (JS 변경 포함) | 기각 |

**채택 근거.** 계획서 §8이 이미 "4에서 한 번 멈춘다"를, §6이 "T4는 써본 뒤 정한다"를 자답하고

**기각된 주장 3건.**

| 주장 | 판정 | 근거 |
|---|---|---|
| C: "JS 변경은 필드 1개 6곳" | **과소평가** | 사이트 수는 정확하나 `candidatesFor():441`이 `e.when`을 버려 반환 계약 자체를 바꿔야 한다 (§3-2-1 ③) |

## 8. 순서

```
Swift 단독 ─┬ 1. startCutIn(_:) 일반화 + 기존 진화 경로 이관  ← 동작 변화 없음, 순수 리팩터
            ├ 2. shouldFire / resolveCutIn 순수 함수 + 테스트
            ├ 3. cutin-seen.json 영속화
            └ 4. T2 리미트 진입 배선 (stale 게이트 포함)      ← 여기서 첫 실사용 가치
                 ─────────────────────────── 여기서 한 번 멈추고 써 본다 ───────────
JS 동반    ─── 5. (보류) T3 케어미스 — route 엔트리 플래그부터
Swift 단독 ─── 6. (보류) T4 인사 — §6-1 결론 후
```

1~2는 동작을 바꾸지 않으므로 따로 커밋해 리뷰 부담을 낮춘다. 실제 가치는 4에서 처음 나온다.

**4에서 한 번 멈추는 것이 이 순서의 요점이다.** 1~4는 Swift 단독에 되돌리기 쉽고, T2 하나만으로
"컷인을 늘린다"는 가설이 검증된다. 5는 JS 계약을 건드리므로 비용 계단이 다르고, 6은 애초에
필요한지가 불확실하다(§6). **T2를 며칠 써 보고 성가시면 5·6은 하지 않는 것이 정답이다** —
이 계획의 §1 논증대로라면 트리거를 늘리는 것 자체에 수확 체감이 있어야 정상이다.

### 8-1. 필수 구현 조건 (판결의 유효 조건)

아래를 지키지 않으면 §5-2의 판결은 무효다. 그때는 범위를 다시 논의한다.

1. **1~4만 구현한다.** 이번 커밋에서 `lib/daily.js`는 건드리지 않는다 — `candidatesFor`의

2. **`shouldFire` / `resolveCutIn` 테스트 없이 T2를 배선하지 않는다.** 이 순수 함수 분리가

3. **T2에 stale HUD 게이트를 반드시 포함한다** (§4-2-1). 오발화하는 컷인은 트리거가 없는

4. **T3·T4는 T2 실사용 며칠 뒤에만 재결정한다.**

### 8-2. 재결정 게이트 — 무엇을 보고 판단하는가

며칠 뒤 아래 셋 중 어디에 해당하는지로 다음 단계를 정한다.

| 관찰 | 해석 | 다음 |
|---|---|---|
| T2가 적당히 뜨고 유용했다 | 가설 검증됨 | T4 재개 검토 (§6-1의 하한선 논거) |

미루는 것이지 검증하는 것이 아니다.
