# 계획: 전역 진화 그래프 + 지연 진화 (Phase B → Phase A)

작성 2026-08-19. 선행 완료: D7(#23, `81a3f5f`). `docs/evolution-routes.md`와 짝을 이루는
문서다 — 그쪽은 팩 단위 랜덤 진화의 현재 계약을, 이 문서는 팩 경계를 없애는 다음 단계를 다룬다.

## 0. 목표

**알 하나에서 시작해, 모든 진화 분기가 그 순간의 조건으로 결정되는 단일 그래프.**
팩은 계보의 소유자가 아니라 표시 뷰로 축소된다.

```
digitama ─[조건]→ 유년기 ─[조건]→ 성장기 ─[조건]→ … ─[조건]→ 종점 또는 초궁극체
```

## 1. 왜 — 지금 무엇이 막고 있나

`pack.json` 하나가 세 관심사를 겸하고 있다.

```
pack.json ─┬─ 계보 그래프      (tree: 노드 + 조건 엣지)
           ├─ 표시 이름        (name, stageNames)
           └─ 도트 파일 소유   (sprite prefix → <pack>/<prefix>-N.png)
```

세 번째가 첫 번째를 인질로 잡는다. 렌더러가 자산을 `<팩 디렉터리>/<prefix>-N.png`
(초상은 `portrait-<prefix>-N.png`)로 찾으므로 노드는 팩 디렉터리에 물리적으로 속해야 하고,
그래서 그래프도 팩 안에 갇힌다. 결과:

- 같은 개체가 팩마다 별개 노드로 복제된다 — 오메가몬(아구몬·파피몬), 베르제브몬(임프몬·케라몬).
  베르제브몬은 sprite prefix까지 갈라져 있다(`ultimate` vs `ultimate-beelzebumon`).
- 라인 교차가 불가능하다. `id`는 "팩 안에서 유일", 엣지 `to`는 "같은 팩의 노드"가
  문서화된 계약이고(`docs/evolution-routes.md` §3), `validatePackTree`의 `unknown-target`이
  팩 밖 참조를 거부한다.
- **로키가 조건이 아니라 제비뽑기로 결정된다.** `selectMon`이 날짜 해시 셔플 덱으로 오늘의
  팩을 먼저 고르므로 `digitama → 유년기 → 성장기` 세 칸에는 조건 판단이 아예 없다.
- 도달하지 않은 칸이 `route`에 미리 채워져 밖에서 보면 미래가 확정된 것처럼 보인다.

## 3. Phase B — 그래프와 자산을 분리한다 (✅ 완료, 2026-08-20)

### B-1 데이터 구조 — 관계는 자식이 소유한다

```
evolution-graph.json          전역 노드 (단일 진실)
sprites/nodes/<id>-{0,1}.png  노드 단위 도트
sprites/nodes/portrait-<id>-*.png
sprites/packs/<rookie>.json   뷰 — 시작 노드 + 표시 이름 (tree 제거)
```

노드는 `{ id, name, stage, sprite, evolvesFrom: [{ from, when }] }`다. **엣지를 부모가
`evolutions`로 내보내지 않고 자식이 `evolvesFrom`으로 받는다.** 같은 엣지 집합의 역인접
리스트지만, 소유자가 바뀌는 것이 이 설계의 핵심이다.

```json
{
  "id": "beelzebumon", "name": "베르제브몬", "stage": "ultimate", "sprite": "beelzebumon",
  "evolvesFrom": [
    { "from": "myotismon", "when": null },
    { "from": "mummymon",  "when": { "type": "topSharePct", "gte": 60 } },
    { "from": "infermon",  "when": null }
  ]
}
```

**왜 방향을 뒤집나.**

- "쿠즈하몬이 될 수 있는 개체"가 쿠즈하몬 한 곳에 모인다. 지금은 그 정보가 부모 팩마다
  흩어져 있고 팩 경계를 넘지 못한다(`unknown-target`이 거부한다). 부모를 추가하려면 부모
  노드를 고쳐야 하고, 부모가 다른 팩이면 아예 불가능하다.
- **Wikimon과 데이터 모양이 같아진다.** `Evolves From` 표는 원래 부모별로 단서를 갖는다
  (`* [[Mummymon]]<ref name=DSLE/> (with or without [[Matadrmon]]<ref name=DSSM/>)`).
  §10.1 게이트 판정이 **자식 페이지 한 장**에서 끝난다.
- **조건이 부모별로 다른 실제 사례가 이미 있다.** 베르제브몬(뱀파이몬 무조건 / 미이라몬
  `topSharePct ≥ 60` / 인펠몬 무조건), 블랙래피드몬(가르고몬 `failureRatioPct ≥ 5` /
  프라리몬 무조건). 조건을 엣지가 아니라 **노드 단위**로 두는 대안은 이 둘을 표현할 수
  없다 — 노드에 조건을 걸면 스파인의 무조건 진화까지 막혀 도달 보장이 깨지고, 안 걸면
  특수 분기가 사라진다. 그래서 `when`은 `evolvesFrom` 항목마다 붙인다.

**`terminal` 플래그가 소멸한다.** "다음 칸에 나를 부모로 지목한 노드가 없으면 종점"이
데이터에서 자동 도출된다. D7이 플래그를 필수화한 근거는 "`evolutions: []`가 의도된 종점인지
후속을 깜빡한 데이터 누락인지 구분할 수 없다"였는데, 이 모델에는 빈 출구 배열이 존재하지
않는다. `docs/evolution-routes.md` §8 D7의 `terminal: true` 계약과, D8이 케라몬 베르제브몬에
넣은 플래그는 이 전환에서 함께 제거된다.

### B-1.1 판단 노드 — 후보 풀은 선언이 아니라 파생이다

진화 직전 판단은 **이미 존재한다.** `walk`이 30초마다 재계산하고 도달한 칸만 잠근다. 바꾸는
것은 판단 시점이 아니라 **후보 풀의 출처**다. 지금 `candidatesFor`는 후보를 그 노드가 미리
선언한 엣지로 좁힌다(`lib/daily.js:417-426`) — 그래서 fan-out이 1이면 판단할 것이 없고 그
칸은 결정론이 된다.

```
후보 = 다음 칸의 노드 중 evolvesFrom 에 현재 노드를 부모로 가진 것
met  = 그 중 해당 항목의 when 이 오늘 지표를 만족하는 것
pool = met.length ? met : 후보 전체       ← 기존 폴백(lib/daily.js:421) 의미 보존
승자 = pool[0].when 과 같은 조건 그룹에서 hashString 타이브레이크  ← 기존 pick 그대로
종점 = 후보가 0개
```

`byId`는 그대로 쓰고, 로드 시 **역인덱스 `childrenOf: 부모 id → [{ node, when }]`** 를 1회
구성한다. 조건 엔진(`conditionMet`)·타이브레이크(`pick`)·미매칭 폴백은 전부 재사용된다 —
바뀌는 것은 후보를 어디서 긁어오는지 한 곳뿐이다.

**도달 보장이 공짜로 성립한다.** 폴백이 "조건에 맞는 후보가 없으면 후보 전체"이므로, 나를
부모로 지목한 노드가 1개 이상이면 반드시 진화한다. 지금 그 역할을 하는
`missing-unconditional-edge` 규칙(각 노드의 마지막 엣지가 `when: null`이어야 한다)이 필요
없어진다.

### B-2 런타임 호환 — 이것이 설계를 결정한다

`route`에 실리는 값은 **계속 전부 문자열**이고 `sprite`는 **팩-상대 prefix**로 내보낸다.
그러면 메뉴바는 지금처럼 `<현재팩>/<prefix>-N.png`를 읽어 **무변경**이고, 사용자가 손빌드해
상주시키는 **구형 바이너리도 무손상**이다.

- `scripts/materialize-sprites.js` 신설 — `sprites/nodes/`를 각 팩이 필요한 노드에 맞춰
  팩 디렉터리로 복사(또는 하드링크)한다. 도트는 gitignore 대상이라 물리 중복은 무비용이고,
  이 저장소가 이미 쓰는 파생물 패턴이다(맵 HTML, 추출 스크립트).
  **팩 경계를 넘는 엣지를 추가하면 `node scripts/materialize-sprites.js --write`를 다시
  돌려야 한다.** 안 돌리면 조건이 발동하는 날 프레임이 없어 한 단계 아래로 폴백하고,
  사용자에게는 퇴화로 보인다. `python3 scripts/sprite_status.py --check` (exit code 확인)가
  이 누락을 잡는다. 2026-08-20 §B-6 편입에서 실측: guilmon/veemon 팩에
  shinegreymon_burst 렌더 경로 누락 → materialize 재실행으로 해소 (8장 복사).
- 대안 (a) "Swift를 `sprites/nodes/`를 직접 읽게 바꾼다"는 **B 이후 별도 결정**으로 미룬다.
  깨끗하지만 D7에서 겪은 롤아웃 창이 다시 열린다(구형 바이너리가 파일을 못 찾아 한 단계
  아래 프레임으로 폴백 → "진화했는데 퇴화"로 보인다).

### B-4 B만으로 즉시 얻는 것 — 도트 0장

> 잘못된 프레이밍이었다. ① 그 +2는 전부 `베르제브몬 → 아마게몬`이라는 **가짜 엣지** 하나에서
> 나왔다(§8 D8에서 제거 — 지표가 허술해서 가짜 엣지가 성과로 계상됐다). ② 더 근본적으로,
> 경로 수는 갈래가 아니라 **말단 조합**을 센다. 일직선 라인을 이어 붙이기만 해도 올라가므로
> "자유로운 진화"의 대리 지표가 못 된다. 세야 할 것은 **분기점(fan-out ≥ 2 노드) 수**와
> **조건부 엣지 비율**이다.

- **궁극체 17칸 전부 분기점이 0개다.** 다음 칸에 초궁극체가 11개 있는데 각 궁극체는 하나만

- **유아기도 0개다.** 오늘의 팩이 정해지면 유년기까지 일직선이다.
- 알의 fan-out 10은 병합이 만들어준다. 조건이 없을 뿐이다 — **자리를 만드는 것이 Phase B,
  거기에 조건을 거는 것이 Phase A**다.

> **`evolvesFrom` 모델에서 이 표를 읽는 법(§B-1).** fan-out은 더 이상 노드가 선언하는 값이
> 아니라 역인덱스에서 파생되는 값이다 — "나를 부모로 지목한 다음 칸 노드 수". 따라서
> "궁극체 분기점 0"은 **궁극체가 자식을 안 적었다**가 아니라 **초궁극체 11개 중 어느 것도
> 두 번째 궁극체 부모를 적지 않았다**로 읽어야 한다. 고칠 자리가 부모가 아니라 자식이라는
> 뜻이고, 그래서 후속 작업의 조회 방향도 뒤집힌다(§B-6).

### Phase B의 목표를 다시 쓴다

경로를 늘리는 것이 아니라 **도트 0장으로 분기점을 만드는 것**이다. 라인 교차가 가능해지면
분기점 단가가 "도트 한 장 + 노드"에서 "엣지 한 줄"로 떨어진다. 이번 D9(`미이라몬 →
베르제브몬`)가 팩 안에서의 첫 사례다 — **시트 0장, 분기점 +1, 초궁극체 도달 경로 +1.**
전역 그래프에서는 같은 일이 팩 경계를 넘어 가능해진다.

부수 효과로 초궁극체에 닿는 경로도 **25 → 26**이 된다. D8 이후 케라몬 라인은 궁극체
베르제브몬에서 끝나는데(블래스트 모드가 임프몬 팩에 있어 팩 격리 상태에서는 표현할 수 없다),
병합하면 그 종점이 풀린다.

**단, 갈래 개수의 상한은 여전히 정사가 정한다.** `evolvesFrom`으로 방향을 뒤집어도 없던
부모가 생기지는 않는다 — fan-out을 늘리려면 자식이 부모를 더 적어야 하고, 그것이 정사에
있는지가 §10.1 게이트다. Phase B가 실제로 바꾸는 것은 **관리 비용**이다. 지금은 부모 팩마다
편집해야 하고 팩 경계를 넘지 못하는데, B에서는 자식 노드 한 곳에 부모를 나열하면 끝이다.
그래서 "정사에 있는 부모를 전부 적는다"가 처음으로 실행 가능해진다.

```

뱀파이몬 ─┐                                뱀파이몬 ─┐
미이라몬 ─┴→ 베르제브몬 → 블래스트 모드       미이라몬 ─┼→ 베르제브몬 → 블래스트 모드

```

케라몬 라인이 블래스트 모드에 닿는다 — Q1이 이 엣지를 유지로 종결했기 때문에 성립한다(§2).
그리고 `terminal: true`(케라몬 베르제브몬)는 병합 시 제거해야 한다 — 병합 후에는 종점이
아니다(§8 D8).

그리고 이후 모든 편입의 단가가 내려간다. 티라노몬을 한 번 넣으면 아구몬·길몬 양쪽에서
엣지 한 줄로 재사용된다. 지금은 두 팩에 노드와 도트를 각각 넣어야 한다.

### B-4.1 Phase B 구현 결정 3건 (계획서에 없던 것들)

#### 결정 1: 노드 배열 순서 = 분기 우선순위 정본

`evolvesFrom` 모델에는 부모 쪽 우선순위를 적을 자리가 없다. 지금 런타임은 부모의 `evolutions` 배열에서 조건을 충족한 **첫** 엣지의 조건 그룹을 승자로 삼는데, 반전하면 그 순서가 사라진다.

실측으로 부모 67개 중 1개가 어긋났다 — 브이몬에서 `sessionCount ≥ 5`(매그너몬)와 `topSharePct ≥ 60 & sessionCount ≥ 2`(화염드라몬)가 **동시 충족**되는 날 승자가 뒤집혔다.

**해결:** 역인덱스 순서 규칙을 ① 노드 배열 순서 ② 조건부 엣지가 무조건 엣지보다 앞(안정 정렬)으로 못 박고, `scripts/migrate-packs-to-graph.js`가 레거시 순서와의 동등성을 강제한다(어긋나면 종료 코드 1). 위상 정렬이 사이클을 만나면 전역 배열 순서로 표현이 불가능하다는 신호이고, 그때는 `evolvesFrom` 항목마다 명시적 `priority`가 필요하다 — 현재 데이터에는 없어서 미뤘다.

**왜 ②가 필수인가:** 무조건 엣지는 항상 조건을 충족하므로, 역인덱스 배열의 첫 자리에 무조건 엣지가 오면 조건부 분기가 **전부 죽는다**(`lib/daily.js:418` 폴백이 항상 전체 후보를 반환).

#### 결정 2: `pack.json`의 `tree` 제거 순서

런타임과 같은 커밋에서 지우면 도트 파이프라인이 같이 죽는다 — `scripts/sprite_status.py`가 레거시 접두사 파일(`adult-0.png` 등, 구형 바이너리 폴백 경로라 의도적으로 안 지웠다)을 "알려진 레거시"로 분류하는 데 `tree`를 쓴다. 그래서 순서는 **런타임/소비자 이관 → 레거시 접두사 파일 정리 → `tree` 제거**다.

#### 결정 3: 골든 스냅샷으로 의미론 전환을 증명하는 절차

교체 **전에** 구 런타임으로 팩 10 × 날짜 8 × ctx 48 = 3840 케이스의 루트를 채집해 `test/fixtures/route-golden.json`에 얼려 두고, 신 런타임이 그것을 재현하는지 회귀로 박았다.

결과: 3840 케이스 × 7칸 = **26,880 비교에서 차이 1종 256건** — 케라몬 초궁극체가 `beelzebumon` → `beelzebumon-bm`으로 바뀐 것뿐이고, 이는 계획서 §B-4가 예고한 **의도된 개선**(팩 격리 때문에 끊겼던 라인이 병합으로 이어진다, 초궁극체 도달 경로 25 → 26)이다.

**교훈:** ctx 축 값 선정에 경계 위/아래만 쓰면 안 되고 **중간값**이 필요하다 — 화염드라몬(`sessionCount ≥ 2`)은 축이 {0,5}뿐이면 매그너몬(`≥ 5`)에 항상 가려 한 번도 등장하지 않아 우선순위 회귀를 못 잡는다.

### B-7 케어미스 게이트 — 쓰레기 계열을 제비뽑기에서 빼낸다 (2026-08-24)

**발단.** 2026-08-24 파피몬 라인 성숙기가 레어몬으로 뽑혔다. 원작에서 레어몬은 방치·케어미스의
산물인데, 이 그래프에서는 파피몬의 성숙기 자식 22개가 **전부 `when: null`** 이라 순수 날짜 해시
추첨이었다(`hashString("2026-08-24|gabumon|adult") % 22 = 10`). §0 목표("조건으로 결정되는 단일
그래프")에 정면으로 반하는 자리다 — 캐논이 "네가 안 돌봤다"고 말하는 노드를 제비뽑기로 주고 있었다.

**축 선정: `outputPerTurn ≥ 15000`.** 턴당 산출이 크다 = 사용자 프롬프트 없이 혼자 굴러간 날 =
방치. sage 특성(턴 ≥80 · ≤6000/턴, 잘 돌본 날)의 정반대 극이라 의미가 겹치지 않는다. 성숙기 도달
조건이 `dailyOutputTokens ≥ 100k`(또는 sage)이므로 게이트가 참인 성숙기 날은 **프롬프트 6개 이하로
10만 토큰** — autopilot·ralph류 무인 주행 날이 정확히 여기 걸린다.

기각한 축 3개 (전부 §10.1 ⓒ 도달 불가 규칙):

| 기각 축 | 근거 |
|---|---|
| `failureRatioPct ≥ 5` | ① 기각 당시(2026-08-20) 의미상 최적이지만 **실측으로 죽은 축**이었다 — `global.json` 46,987 성공 / **0 실패**, 영구 0%. §Q4가 누적 축으로 분류한 그대로였다. 원인은 축의 성질이 아니라 배선 누락(`PostToolUse`는 성공에만 발화, 실패는 `PostToolUseFailure`가 담당하는데 미배선)이었고, **2026-08-24 배선 수정 + 세션 합산 전환으로 이 축은 이제 하루 안에서 움직인다**(`docs/evolution-routes.md` §Q4 참고) — 다만 이 기각 자체는 ②의 축 충돌이 별도로 유효하므로 뒤집지 않는다. ② gabumon 스파인 상류 충돌: 참일 때 성숙기가 레어몬으로 새면 가루몬을 우회해 완전체 블랙워가루몬이 도달 불가가 된다(다크드라몬 사례와 동형). |
| `all: [topSharePct ≤ 25, sessionCount ≥ 5]` | 기존 `sessionCount ≥ 5` 엣지의 **부분집합**이 되어 agumon·impmon 스파인에서 사문화된다. 노드 배열 인덱스가 지오그레이몬 22 · 이블몬 28 vs 누메몬 233 · 레어몬 256 · 스카몬 265이므로 두 조건이 동시에 참인 날 항상 진다(§B-4.1 결정 1). |
| `dailyOutputTokens ≤ N` | 성숙기 도달 조건이 이미 `≥ 100k`이라 sage 날에만 참이 된다 — sage 축과 중복이고 의미가 뒤집힌다(방치가 아니라 설계 날). |

**게이팅 방식: in-edge 전량.** `readGraph` 정렬 규칙 2(조건부 엣지가 무조건 엣지 앞)가 조건 하나로
두 가지를 동시에 만든다 — 참이면 `pool[0]`이 케어미스 엣지라 무조건 형제들이 `tied`에서 빠져
**확정**되고, 거짓이면 케어미스 엣지가 `met` 필터에서 빠져 **추첨에서 제외**된다. 그래서 한 노드의
in-edge를 전량 게이팅하면 그 노드는 "게이트 밖에서 도달 불가"가 된다.

| 노드 | 칸 | 게이팅 | in-edge |
|---|---|---|---|
| 누메몬 | 성숙기 | 전량 | 17 |
| 레어몬 | 성숙기 | 전량 | 8 |
| 스카몬 | 성숙기 | 전량 | 6 |
| 게르베몬 | 완전체 | **부분** — 위 3개 부모로부터만 | 3 / 11 |

게르베몬만 부분 게이팅인 이유: 나머지 8개 부모(아큐라몬·가오가몬·지오그레이몬·가드로몬·키위몬·

풀이 줄어든다.

**제외한 케어미스 후보:**

  이어지지 않고(운석몬은 케어미스가 아니다) 운석몬만 파피몬 스파인에서 케어미스 전용이 된다. 이득 0.

## 4. Phase A — 지연 진화를 완성한다 (착수 조건: Phase B 완료 ✅)

**착수 가능.** Phase B가 완료됐으므로 전역 그래프(`evolution-graph.json`)가 존재하고, 로키에 조건을 걸 노드 모음이 준비됐다. D3 보류 근거("D2와 상충")가 D7의 D2 완화로 소멸했다.

성장기 위 구간은 **이미** 진화 직전 판단이다. `selectRoute`가 30초마다 재계산하고 도달한 칸만
핀되므로, 잠기는 값은 그 순간의 지표로 판단된 값이다(테스트
`selectRoute locks the reached stage against condition changes but leaves the rest open`).
남은 것은 두 개뿐이다.

### A-1 로키를 조건으로 결정한다

`selectMon` 폐기. 유아기 10개 노드가 각자 `evolvesFrom: [{ from: "digitama", when: … }]`를
갖는다 — 로키 선택이 곧 알의 판단 노드가 된다. **B가 선행조건인 이유가 이것이다.** `id`가
전역이어야 10개 노드가 같은 부모를 지목할 수 있고, 그래야 알 밑에 조건을 걸 자리가 생긴다.

**결정 시점 문제**: 성장기는 output 30K에서 잠긴다(유년기는 1토큰). 그 시점에 오늘을 판별할
지표가 거의 없다 — 세션 수·집중도·턴당 출력은 모두 하루가 지나야 의미가 생긴다. 이것이
애초에 로키가 날짜 해시였던 이유다.

→ **초반 엣지는 누적·어제 지표로 판단한다.** 회피가 아니라 "성장 배경"의 정의 그대로다.
신규 조건 타입 후보: `yesterdaySessionCount`, `yesterdayTopSharePct`,
`recentFailureRatioPct`(N일 창), 기존 `consecutiveDaysActive`·`milestone`.

**잃는 것**: 셔플 덱 로테이션과 `mon-history.json`이 존재 이유를 잃는다(`81a3f5f`에 방금
들어간 작업이다). 로키가 지표로 결정되면 "고르게 등장"은 목표가 아니고, 지표가 편향돼
있으면 특정 로키가 계속 나오는 것이 **정상**이 된다. 이 교환을 받아들이는 것이 A-1의 실질이다.

### A-2 미확정 구간을 비운다

`route`에 도달한 칸까지만 기록한다. `daily.json`이 하루에 걸쳐 자란다.

- 메뉴바는 route 변경 시 프레임을 다시 읽으므로 커지는 route를 견딘다. `applyRoute` 캐시
  키에 name이 포함된 것은 #23에서 이미 들어갔다.
- 맵의 "오늘의 루트"가 **걸어온 경로 + 가능한 미래**로 바뀐다.

### A-3 멱등성 포기를 명문화한다

지금은 날짜+지표로 언제든 재계산 가능하다. 완전 지연 평가는 "그 순간의 값"에 의존하므로
`daily.json`을 지우면 복원할 수 없다. lazy binding이 이미 부분적으로 그렇지만(핀된 접두부),
전면화하면 완전히 상태 의존이 된다. `Math.random` 금지는 유지한다 — 같은 `daily.json` +
같은 지표면 같은 결과여야 한다.

  지점이다. 충분한 확장 이후 재검.~~
  **재검 완료, 트리거를 이미 넘었다 (2026-08-20, 235종 편입 후 79 → 314 노드, 이후
  초궁극체 칸 승격 14종 반영).** 실측(`readGraph` + `evolvesFrom` 전수 스캔): **fan-out
  ≥ 4인 부모 111개**, 최대는 여전히 **아구몬(28)** — "아구몬 6갈래"를 한참 지나 28갈래가
  됐다. **조건 축을 늘려야 할 압력은 없다 — 그러나 이유가 "괜찮아서"가 아니다.** 신규
  엣지가 전부 `when: null`이라 조건 축 5개가 부족해지는 상황 자체가 생기지 않는 것뿐이고,
  이는 **신규 분기에서 조건 결정을 통째로 포기했기 때문에** 축 압력이 안 생기는 것이다.
  그 결과 1105개 엣지 중 1088개(98.46%)가 조건이 아니라 `hashString(날짜|팩|단계)`
  제비뽑기로 갈리게 됐다 — §0이 내건 목표("모든 진화 분기가 그 순간의 조건으로 결정되는
  단일 그래프")에서 오히려 후퇴했다.
  실측 도달률(팩 로키 10종 × 336일, `selectRoute` 시뮬레이션): 초궁극체 도달률
  **90.0% → 18.7% → (초궁극체 칸 승격 14종 반영 후) 41.4%**로 절반 이상 회복됐다(궁극체
  이상 87.3%, 완전체 이상 97.9%). 다만 예전 79노드 시절엔 사용량과 무관하게 90%로
  고정이었던 것과 달리, 지금은 **사용량 구간에 따라 갈린다** — 중간 사용량 32.1% / 중상
  33.5% / 최대 41.4%. 즉 후퇴분은 회복됐지만 "결정론적으로 90%"가 아니라 "사용량이 늘수록
  올라가는 41.4%까지"로 성격이 바뀌었다. 이것은 사용자가 노드 수 확장을 우선해 **명시적으로
  승인한 트레이드오프**다(초궁극체가 희귀 보상이 되는 것을 그대로 둔다는 결정). 되돌리려면
  런타임 후보 선택에 "등반 가능한(초궁극체까지 닿는) 자식을 우선"하는 규칙을 넣는
  선택지가 있다 — 아직 미착수, 후속 항목으로 남긴다.
  뒷받침 수치: 조건부 엣지 절대 수는 병합 전(94개 엣지 중 17개=18.09%)과 편입 후
  (1105개 엣지 중 그대로 17개=1.54%)가 같다 — 새로 추가된 조건부 엣지는 0개이고, 비중만
  분모가 커지면서 희석됐다. 조건 축이 실제로 동작을 좌우하는 지점은 여전히 옛 90개
  엣지뿐이다. 종점(out-degree 0) 노드는 109 → 89개로 줄었다(승격 14종 중 다수가 종점
  판정에서 벗어남).
  **정정 (2026-08-24).** 위 "하루 단위로 의미 있는 조건 축은 5개, `failureRatioPct`는
  누적값이라 하루 안에서 안 움직인다"는 서술은 더 이상 맞지 않는다. 원인은 `PostToolUse`가
  성공에만 발화하고 실패는 `PostToolUseFailure`가 맡는데 그 배선이 빠져 있던 것이었다(README
  훅 설정 오기재도 함께 수정됨). `PostToolUseFailure` 배선과 `lib/daily.js`의 세션별 상태
  파일 합산(`sessionToolCounts`)이 들어가면서 `failureRatioPct`는 하루 안에서 움직이는
  **6번째 일일 축**이 됐다. 상세는 `docs/evolution-routes.md` §Q4.
